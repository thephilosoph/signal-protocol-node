## 1. The problem: end-to-end encryption

TLS encrypts traffic between two *machines*, but a chat server still sees your plaintext. **End-to-end encryption (E2EE)** means only the endpoints hold the keys: the server relays ciphertext it cannot read.

That raises a question TLS never has to answer: **how do two strangers who have never exchanged anything establish a shared secret asynchronously?** Alice cannot call Bob to agree on a key — Bob might be offline for a week. And it is not enough to establish the secret *once*: if Alice's phone is stolen tomorrow, yesterday's messages must stay safe, and the conversation must *heal* after a compromise.

The Signal Protocol answers both questions with two algorithms:

- **X3DH** (Extended Triple Diffie-Hellman) — the initial handshake with an offline stranger.
- **The Double Ratchet** — per-message key evolution for the rest of the conversation.

## 2. The key ideas

Everything rests on one property of **Diffie-Hellman key agreement** over elliptic curves (X25519):

> Given Alice's private key `a` and Bob's public key `B = b·G`, both Alice and Bob can compute the same shared value `a·B = b·A = ab·G`. An eavesdropper who sees only `A` and `B` cannot compute it.

Two consequences drive the whole design:

1. **Combining DH outputs** — you can mix several independent DH results (hash them together) into one strong secret.
2. **Ratcheting** — each new DH turn creates a *new* secret unrelated to the previous one; compromise of the current secret does not reveal future or past ones.

And one property of **hash chains** (the "symmetric ratchet"): from a chain key `CK`, derive

```
MK  = HMAC(CK, 0x01)   // the message key
CK' = HMAC(CK, 0x02)   // the next chain key
```

You can move forward (derive message keys one by one) but you cannot go backward: from `CK'` you cannot recover `MK` already used or earlier keys. That is the "ratchet" — it only turns one way.

## 3. Prekeys: being reachable while offline

Alice's problem: Bob is offline, but she wants to send him an encrypted message *today*.

The solution: Bob publishes, via the app's server, a **prekey bundle**:

| Component | What it is | Lifetime |
| --- | --- | --- |
| **Identity key (IK)** | Long-term key pair, the "real" identity of Bob | Years |
| **Signed prekey (SPK)** | A second X25519 key pair, **signed** by the identity key | Weeks/months |
| **One-time prekeys (OPK)** | A pool of pre-generated X25519 keys, each used at most once | Until consumed |

In this library those are exactly what `getPreKeyBundle()` produces — a JSON object containing the identity keys, the signed prekey + its Ed25519 signature, and (optionally) one one-time prekey:

```json
{
  "version": 1,
  "identity": { "dhKey": "...", "signingKey": "..." },
  "signedPreKey": { "id": 3, "publicKey": "...", "signature": "..." },
  "oneTimePreKey": { "id": 41, "publicKey": "..." }
}
```

The server stores bundles and hands each one-time prekey out **at most once**. When Alice starts a session she consumes one; when Bob later decrypts, the private half is still waiting on his side. The pool gets refilled (`generatePreKeys`, or `topUpOneTimePreKeys` in the NestJS service).

**Why the signature?** Anyone can upload a fake bundle for Bob's address. The Ed25519 signature proves the signed prekey was generated by the holder of Bob's identity key — Alice's client verifies it before trusting the bundle (`SignatureVerificationError` otherwise).

## 4. X3DH: agreeing on a secret with a stranger

With Bob's bundle, Alice computes **three or four** independent Diffie-Hellman outputs and hashes them together:

```
DH1 = DH(IK_A,  SPK_B)     // Alice's identity key with Bob's signed prekey
DH2 = DH(EK_A,  IK_B)      // a fresh ephemeral key with Bob's identity key
DH3 = DH(EK_A,  SPK_B)     // Alice's ephemeral with Bob's signed prekey
DH4 = DH(EK_A,  OPK_B)     // (only if Bob had a one-time prekey available)

SK  = HKDF(DH1 || DH2 || DH3 [|| DH4], salt = 0^32, info = "…x3dh…")
AD  = IK_A || IK_B         // "associated data" = both identity keys
```

`EK_A` is a brand-new key pair Alice generates just for this handshake and never reuses.

Why so many DHs? Each one covers a compromise scenario the others don't:

- **DH2/DH3 (with the fresh ephemeral)** — even if Bob's signed prekey private key leaks later, Alice's ephemeral keeps the handshake secret.
- **DH1** — ties the session to both parties' *long-term* identities (mutual authentication).
- **DH4 (one-time prekey)** — makes the handshake forward-secret even if Bob's signed prekey is compromised *before* Alice ever sends a message. This is why one-time prekeys exist.

`SK` becomes the initial root key of the Double Ratchet. `AD` (the two identity keys concatenated) is not secret — it is bound into every subsequent message's AEAD authentication so ciphertexts cannot be transplanted between identities or sessions.

**Bob's side.** The X3DH material travels *inside the first encrypted message* (a `prekey` envelope). When Bob receives it he looks up which signed prekey and one-time prekey were used (`signedPreKeyId`, `oneTimePreKeyId`), recomputes the same DHs in the same order from his own private keys, and arrives at the same `SK`. One message, two jobs done: handshake and first payload.

In this library the whole dance is `alice.createSessionFromBundle('bob.1', bundle)` followed by `encrypt` — see `src/x3dh/x3dh.ts` for the implementation.

## 5. The Double Ratchet: a key per message

After X3DH both sides hold `SK` — but if they kept encrypting with keys derived from `SK` alone, one compromise would expose the whole conversation. The Double Ratchet adds **two ratchets that advance constantly**:

### The symmetric ratchet (every message)

Each direction of the conversation has a **chain key**. Every message:

```
MK  = HMAC(CK, 0x01);  CK' = HMAC(CK, 0x02)      // turn the ratchet
ciphertext = AES-256-GCM(key = HKDF(MK), nonce = HKDF(MK), plaintext, AD || header)
```

Every single message uses a unique key. The used key is immediately consumed — there is no way to derive it again from later state, so **a key compromise never exposes previous messages** (*forward secrecy*).

### The DH ratchet (every time the direction flips)

Additionally, the header of each message carries the sender's current **ratchet public key**. When Bob receives a message whose header key differs from the one he knows, that's Alice's signal "I've turned my DH ratchet", and he:

```
new receiving chain = HKDF-RK(RK, DH(my RatchetKey, Alice's new key))
my RatchetKey       = fresh key pair                    // turn the DH ratchet
new sending chain   = HKDF-RK(RK, DH(new key, Alice's new key))
```

So every time the conversation changes direction, a *fresh Diffie-Hellman* is mixed into the root key. This gives **post-compromise security** (a.k.a. *self-healing*): if an attacker captures the session state at some point, the conversation they can read is finite — as soon as both parties exchange a few more messages, fresh DH turns re-randomize everything and the attacker is locked out again.

### The message format

```
SignalMessage  = { type: "signal", ratchetKey, previousCounter, counter, ciphertext }
PreKeySignalMessage = { type: "prekey", identityKey, identitySigningKey,
                        baseKey, signedPreKeyId, oneTimePreKeyId?, message }
```

- `ratchetKey` — the sender's current DH ratchet public key (drives the DH ratchet).
- `counter` / `previousCounter` — position in the current chain / length of the previous chain (drives skipped-key handling).
- The header is authenticated: it is part of the AES-GCM associated data, so an attacker cannot tamper with counters or swap ratchet keys undetected.

In this library: `src/ratchet/double-ratchet.ts` implements the state machine; `src/session/session-cipher.ts` wraps it per-session.

## 6. Out-of-order delivery and skipped keys

Real networks reorder packets. If message #5 arrives before #3, Bob must still decrypt both — but he can't rewind his hash chain (that would defeat the ratchet).

The solution: when Bob needs message #5 while his receiving chain is at #2, he *fast-forwards* the chain, storing the intermediate message keys he passes over:

```
advance 2 → 3 → 4 → 5, caching MK₃ and MK₄ as "skipped keys"
decrypt #5 with MK₅
```

When #3 and #4 eventually arrive, they are decrypted from the cache and the used keys are deleted. Two limits keep this bounded:

- `maxSkip` (default 1000) — a counter gap larger than this is rejected (`TooManySkippedMessagesError`) rather than letting an attacker force unbounded memory use;
- the skipped-key cache itself is capped (oldest entries dropped).

The same mechanism covers a subtler case: when Bob's reply triggers a DH ratchet, messages still in flight from the *old* chain would be lost. Before ratcheting, the old chain's pending keys are cached too, and the session keeps a few **archived states** so late stragglers decrypt instead of failing (`archivedStatesLimit`, default 5).

## 7. What an attacker sees

Assume the worst realistic attacker: controls the server, records everything, may compromise a device at a point in time.

| Attack | Outcome |
| --- | --- |
| Reads all traffic | Ciphertext + headers only; AES-256-GCM authenticated encryption |
| Forges a bundle for Bob's address | Rejected: signed prekey signature doesn't verify |
| Tamper with any envelope field | GCM authentication fails (headers are bound into the AD) |
| Replay an old envelope | Rejected: message keys are consumed exactly once |
| Steals Bob's DB *after* the fact | Past messages safe: message keys and root keys ratchet forward only (forward secrecy) |
| Steals Bob's DB, conversation continues | Attacker locked out after the next few DH ratchet turns (post-compromise security) |
| Stole Bob's *identity* key long ago | Can impersonate Bob for *new* sessions; past one-time-prekey-protected sessions still forward secret |
| Swaps Alice's ciphertext into a session with Carol | Fails: associated data binds both identity keys into every ciphertext |

What the protocol does **not** give you (be honest with users):

- **Metadata protection** — who talks to whom and when is visible to the server.
- **Deniability is weaker than stock Signal** — see deviations below.
- **Protection against a malicious local process** — if the machine is compromised, keys are on it.

## 8. How this library maps to the spec

| Signal spec concept | This library |
| --- | --- |
| Identity key (IK) | `IdentityKeyPairDTO.dhKeyPair` (X25519) + `signingKeyPair` (Ed25519) |
| Signed prekey (SPK) | `SignedPreKeyRecordDTO`, signature verified in `parsePreKeyBundle` |
| One-time prekeys (OPK) | `OneTimePreKeyRecordDTO` with `reservedAt` bookkeeping |
| X3DH `SK` | `initiateX3dh()` / `receiveX3dh()` → HKDF of DH1–DH4 |
| Associated data (AD) | `associatedData` in the session record, bound into every AEAD |
| KDF_RK (root ratchet) | `kdfRootKey` = HKDF-SHA256(salt = root key, ikm = DH output, 64 bytes) |
| KDF_CK (chain ratchet) | `kdfChainKey` = HMAC(CK, 0x01) / HMAC(CK, 0x02) |
| Message key → AES material | HKDF(MK) → 32-byte key + 12-byte nonce |
| MKSKIPPED | `RatchetStateDTO.skippedKeys` with `maxSkip` bound |
| Session archive | `SessionRecordDTO.states` (current + archived, promoted on use) |

## 9. Deviations from the original specification

The original Signal spec uses a single X25519 key as the identity key and signs the prekey with it via **XEdDSA** (a scheme that converts an X25519 key into a signing key). This library uses the approach of other Double Ratchet implementations (e.g. Olm/MATRIX): **two identity keys** — X25519 for DH and Ed25519 for signatures.

- **Why:** it avoids implementing XEdDSA, keeps each key single-purpose, and Ed25519 signatures verify without any conversion magic.
- **Consequence:** ciphertext is *not* byte-compatible with libsignal. This is a self-contained protocol family: both peers must use this library.
- **Deniability note:** XEdDSA was designed so signatures are indistinguishable from DH outputs, which strengthens *deniability* (a signed prekey cannot be proven authentic in court). The two-key approach weakens that particular property slightly; session-level deniability of message contents is unaffected since message authentication uses symmetric MACs, not signatures.

Other deliberate choices:

- **JSON envelopes** instead of protobuf — human-debuggable, trivially transportable; switch to binary later without touching the crypto.
- **HKDF info strings** are namespaced (`signal-protocol-node/x3dh/1`, `…/ratchet-root/1`, `…/message-key/1`) and the X3DH info is configurable, so a deployment can domain-separate its protocol.
- **Version byte** in envelope headers and AEAD AD, ready for future format evolution.

## 10. Group messaging: fan-out and Sender Keys

This library ships **both** group strategies behind one API (`SignalGroup.create(client, id, { mode })`).

### 10.1 Fan-out mode (default) — small/medium groups

The sender keeps one Double Ratchet session per member; one `encrypt()` produces one
envelope per member, each under that pair's session keys:

```
alice.encryptGroup("team", "hi")
  → messages["bob.1"]   = SignalEnvelope (session alice↔bob)
  → messages["carol.1"] = SignalEnvelope (session alice↔carol)
  → messages["dave.1"]  = SignalEnvelope (session alice↔dave)
```

Each recipient decrypts their own envelope with the ordinary pairwise `decrypt()` —
the receiving side has **no group protocol at all**.

Security properties:

| Property | Fan-out groups |
| --- | --- |
| End-to-end encryption | ✅ full — every message travels under a real Double Ratchet |
| Forward secrecy | ✅ per pair (each pairwise session ratchets independently) |
| Post-compromise security | ✅ per pair |
| Authenticity of sender | ✅ cryptographic (only the holder of Alice's pairwise sessions could produce the ciphertexts Bob accepts) |
| Cost per message | ❌ O(N) ciphertexts, O(N) ratchet steps |
| Membership enforcement | ⚠️ sender-side + server authorization, not cryptographic |

That last row deserves honesty: fan-out does not make "who is in the group"
cryptographically unforgeable. If the server lets a removed member keep receiving
somebody's fan-out envelopes, that member's client would still reject/ignore them —
but the group's authorization boundary is your server's job, exactly as in the
pairwise case. For hard revocation semantics, rotate the group id and re-invite.

### 10.2 Sender Keys mode — large groups (O(1) per message)

Signal's own group design, implemented in this library as mode `'sender-keys'`:

1. **Distribution.** Each sender generates a fresh symmetric *chain key* and an
   Ed25519 *signing key pair*, and distributes both to every member **encrypted
   through the existing pairwise sessions** (`createDistribution()`). The chain key
   is secret; the signing public key travels with it.
2. **Messages.** Each group message is encrypted **once** with the current message
   key of the sender's symmetric chain (the same HMAC ratchet as the pairwise
   receiving chain: `MK = HMAC(CK, 0x01)`, `CK' = HMAC(CK, 0x02)`, AES-256-GCM with
   the group/distribution/iteration/signing-key bound into the AAD). The sender
   signs header + ciphertext with the distribution's Ed25519 private key.
3. **Receiving.** Members verify the signature (against the distributed signing key),
   advance the sender's chain to the message iteration (skipping and caching keys for
   out-of-order delivery, exactly like the pairwise ratchet), and decrypt. Message
   keys are consumed exactly once — replays fail.
4. **Membership changes.** `rotateDistribution()` generates a fresh chain + signing
   key and redistributes to *current* members only. Removed members never receive the
   new chain: they cannot decrypt (or verify) anything sent afterwards.

Security properties:

| Property | Sender Keys |
| --- | --- |
| End-to-end encryption | ✅ (chain key only ever travels under pairwise sessions) |
| Cost per message | ✅ O(1) — one encryption, one signature |
| Authenticity of sender | ✅ universal — every member verifies the sender's signature (a malicious *member* cannot forge the sender's messages) |
| Forward secrecy | ⚠️ weaker — every member holds the chain key, so a compromised member can decrypt that sender's messages *until the next rotation*; no DH ratchet inside the group |
| Post-compromise security | ⚠️ only at rotation time (membership changes) |
| Replay protection | ✅ message keys consumed once |

The trade-off is the standard bargain: fan-out gives maximal per-message security at
O(N) cost; Sender Keys gives Signal-style scalability with rotation-based healing.
Use fan-out for small groups where you want maximum forward secrecy, Sender Keys for
large groups where O(1) matters. Both modes can coexist in one deployment.
